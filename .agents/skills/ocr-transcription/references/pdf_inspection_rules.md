# قواعد الاستطلاع المسبق لملفات PDF عبر pdf-inspector (Pre-flight Inspection Rules)

يُستعمل هذا المسار قبل خطوة تخيير المستخدم لتعريف الوكيل الرئيسي بنوع ملف الـ PDF (محتوى نصي أو ممسوح ضوئياً أو قائم على الصور أو مختلط) ولتوجيه اختيار المسار الأمثل (مباشر أو عبر الصور) قبل ان يبدأ المستخدم عمله.

---

## ١. تعليمات التثبيت (Install Prerequisites)

الأداة [`pdf-inspector`](https://github.com/firecrawl/pdf-inspector) أداة Rust تُحمَّل مرة واحدة عبر Cargo؛ لا تتضمّن المكتبة حالياً حزماً ثنائية جاهزة (لا توجد GitHub Releases)، فيلزم توفّر سلسلة أدوات Rust على جهاز المستخدم.

```powershell
# ١. تثبيت Rust مرة واحدة (إن لم يكن مثبتاً)
winget install Rustlang.Rustup

# ٢. تثبيت أداة pdf-inspector
cargo install pdf-inspector

# ٣. التحقق من التثبيت
detect-pdf --version
```

- في حال عدم توفّر `detect-pdf` على PATH بعد التثبيت، أضف مجلد `%USERPROFILE%\.cargo\bin` يدوياً إلى متغيّر البيئة `PATH` أو أعد فتح الصدفة لتحميله.
- يحظر على السكربت وعلى الوكيل تثبيت أيٍّ من ذلك بصمت؛ يكتفي بطباعة رسالة خطأ واضحة وإبلاغ المستخدم، انتظاراً لتدخله اليدوي.

---

## ٢. تعليمات الاستدعاء وأوامر التشغيل (Invocation)

يُستدعى السكربت [`pdf_inspect.py`](../scripts/pdf_inspect.py) عبر مسار المهارة المطلق ديناميكياً كما في بقية السكربتات:

```powershell
# فحص شامل (افتراضي: استراتيجية full + تحليل بنية الجداول والأعمدة)
python "<Skill_Dir>/scripts/pdf_inspect.py" "pdf/input.pdf"

# فحص نطاق صفحات محدد
python "<Skill_Dir>/scripts/pdf_inspect.py" "pdf/input.pdf" --pages "1-3,8"

# استراتيجية أسرع للتخمين المبدئي
python "<Skill_Dir>/scripts/pdf_inspect.py" "pdf/input.pdf" --strategy early-exit

# طباعة الـ JSON الناتج على stdout لمعاينة سريعة
python "<Skill_Dir>/scripts/pdf_inspect.py" "pdf/input.pdf" --json
```

- **مجلد الإخراج الافتراضي**: `output_parts/` (نفس مجلد `progress.json`).
- **اسم ملف الإخراج**: `output_parts/inspection.json`.
- **سياسة الفشل**: عند غياب `detect-pdf` على PATH يطبع السكربت رسالة `Error: The 'detect-pdf' CLI ...` ثم تعليمات التثبيت الكاملة، ويخرج برمز `1` — دون محاولة تثبيت صامتة.

## ٣. بنية ملف `output_parts/inspection.json`

يكتب السكربت الملف الناتج بالهيكل التالي (مرجع لاتخاذ قرار المسار):

| الحقل | النوع | الوصف |
|---|---|---|
| `pdf_type` | string | نوع الملف: `text-based` / `scanned` / `image-based` / `mixed`. |
| `confidence` | number | درجة ثقة التصنيف بين `0.0` و`1.0`. |
| `total_pages` | integer | إجمالي صفحات الملف المفحوص. |
| `analyzed_pages` | integer | عدد الصفحات التي شملها الفحص فعلياً. |
| `pages_needing_ocr` | array of int | الصفحات (1-based) التي تفتقر إلى نص قابل للاستخلاص البصري المباشر. |
| `is_rtl` | boolean | هل يحتوي الملف على نص من اليمين إلى اليسار (العربية/الفارسية/العبرية). |
| `has_tables` | boolean | هل رُصدت جداول في البنية (عبر تحليل المستطيل أو الاستدلالات). |
| `has_multi_column` | boolean | هل رُصد تخطيط متعدد الأعمدة. |
| `source_file` | string | المسار المطلق للملف الأصلي (يُضاف تلقائياً بواسطة السكربت). |

> **ملاحظة**: قد تختلف أسماء الحقول أو تُضاف حقول أخرى في إصدارات لاحقة من `pdf-inspector`. يلزم على الوكيل قراءة ملف `inspection.json` كاملاً في كل تشغيل وعدم افتراض ثبات المخطط.

## ٤. مصفوفة قرار المسار (Pipeline Decision Matrix)

يلتزم الوكيل الرئيسي بالمصفوفة التالية لتوجيه المستخدم قبل تخييره:

| نوع الـ PDF | `is_rtl` | المسار الموصى به |
|---|---|---|
| `text-based` | `true` أو `false` | **المسار المباشر (Direct PDF Extraction)** — النص قابل للقراءة عبر `view_file` مباشرة دون الحاجة لتوليد صور. |
| `scanned` | أي قيمة | **مسار صور الـ PDF (PDF Image Pipeline)** — الصفحات صور فقط، ولا بدّ من تحويلها إلى PNG قبل الاستخلاص البصري. |
| `image-based` | أي قيمة | **مسار صور الـ PDF (PDF Image Pipeline)** — مشابه للسابق. |
| `mixed` | أي قيمة | **مسار صور الـ PDF (PDF Image Pipeline)** — يضمن التعامل البصري مع كلٍّ من الصفحات النصية والممسوحة على حدّ سواء. |

يبقى للمستخدم دائماً حقّ التجاوز؛ يُعرض التوصية مع التبرير ولا يُفرض المسار عليه.

---

## ٥. حظر استخراج النصوص عبر pdf-inspector (Hard Ban on `pdf2md`)

1. **يُمنع منعاً باتاً** استخدام الأمر `pdf2md` أو أيّ أمر آخر يُخرج نصوصاً مستخلصة من أداة `pdf-inspector`. فاستخلاص النصوص يظلّ حصراً عبر أداة `view_file` للنموذج، التزاماً بـ [ميثاق النسخ](transcription_rules.md).
2. **يُمنع على الوكلاء الفرعيين (Subagents)** تشغيل سكربت `pdf_inspect.py`؛ فسلطة الاستدعاء محصورة في الوكيل الرئيسي وحده، تطبيقاً لبروتوكول [**execution_rules.md**](execution_rules.md).
3. **لا يُستعمل ملف `inspection.json`** لتوجيه الاستخلاص داخل الصفحات؛ فهو استشاري ويُستخدم حصراً في قرار المسار قبل بدء المعالجة.

## ٦. بروتوكول الفشل (Failure Protocol)

يتبع هذا المسار نفس سياسة [**execution_rules.md**](execution_rules.md) المتّبعة مع `pandoc`:

1. إذا غاب `detect-pdf` أو تعطّل (رسالة على stderr أو كود خروج غير صفري):
   - يتجمّد الوكيل الرئيسي فوراً ولا يقدّر النتيجة ولا يتجاوزها.
   - يطبع السكربت رسالة `Error:` كاملة في stderr، ويتضمّن نصّها:
     - اسم الأداة ومسار البحث عنها.
     - أمر التثبيت اليدوي الكامل (`winget install Rustlang.Rustup` ثم `cargo install pdf-inspector`).
   - لا يُحاول السكربت تثبيت أي شيء بصمت، ولا يعدّل البيئة.
2. إذا أعاد `detect-pdf` مخرجات غير قابلة للتفسير كـ JSON (شذوذ في الإصدار مثلاً):
   - يُسجَّل الخطأ كاملاً ويُعرض على المستخدم.
   - يسأل الوكيل المستخدم صراحة: هل يودّ متابعة العمل **بدون** الاستطلاع المسبق (فيتخطّى الخطوة ويعتمد تخييره التقليدي بين المسارين)، أم يفضّل إصلاح البيئة أولاً؟

---

## ٧. سير المعالجة اللاحقة (Downstream Usage)

- بعد انتهاء الاستطلاع وعرض التوصية، يقرأ الوكيل الرئيسي `output_parts/inspection.json` ويتصرّف وفق مصفوفة القرار.
- لا يُمرَّر هذا الملف إلى الوكلاء الفرعيين؛ فهم لا يحتاجون إلى بيانات التصنيف، بل يقرؤون الصفحات مباشرة عبر `view_file` (سواء كانت صفحات PDF في المسار المباشر أو صور PNG في مسار الصور).
- يُحذف `inspection.json` ضمن عملية التنظيف التي يجريها سكربت `merge_parts.py` عند اكتمال المسار (لأنّه مُخرج مؤقت وليس جزءاً من المنتج النهائي).
